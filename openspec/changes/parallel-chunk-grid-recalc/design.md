## Context

See proposal.md — Why, for motivation. What shapes the approach is what the
decompiled Build 42 code already does and already provides.

The recalculation pass itself is largely instance-local. Extracting
`ReCalculateAll`, `ReCalculateCollide`, `ReCalculatePathFind` and
`ReCalculateVisionBlocked` from `IsoGridSquare` and checking every static they
reach turns up exactly one — `IsoGridSquare.setMatrixBit`, a pure bit function
on an `int`. The arithmetic that dominates the pass has no shared mutable state,
which is why this is worth attempting at all.

The audit (docs/recalc-static-audit.md) added two facts that shape the pool:
the streamer pass is chunk-local (`ChunkGetter` clips every lookup to its own
chunk), and `RecalcProperties` re-runs inside loop 3 via
`RecalcPropertiesIfNeeded`, reaching shared lazy state (`IsoMetaGrid`'s clipper
scratch, lazy singletons, square construction) that only loop 1 warms.

Measurement (docs/archive/2026-09-24/baseline-findings.md) added a third: the streamer thread is
idle >90 % of the time at car speed, and chunk latency is set by
`threadLoop()`'s fixed 140 ms sleeps, not by the pass.

Two pieces of shared state sit around that arithmetic, both on the streaming
path:

1. `IsoChunk.chunkGetter` — `private static final ChunkGetter`, bound with
   `IsoChunk.chunkGetter.chunk = this` for the duration of the recalc pass and
   cleared after, guarded by `assert (IsoChunk.chunkGetter.chunk == null)`.
2. `IsoGridSquare.getNew(cell, slice, x, y, z)` — polls a static
   `isoGridSquareCache` (`ArrayDeque`, not thread-safe) and writes the static
   scratch fields `col`, `path`, `pathdoor` and `vision`.
   `IsoChunk.loadInWorldStreamerThread()` calls this directly.

Usefully, the game already has parameterised overloads of both seams:
`RecalcAllWithNeighbours(boolean, GetSquare)` takes the getter as an argument,
and `getNew(ArrayDeque<IsoGridSquare>, cell, slice, x, y, z)` takes the pool as
an argument. Neither seam has to be invented; the single-threaded callers simply
don't use them.

`WorldStreamer` owns the load queue (`chunkRequests1`, `pendingRequests`,
`jobList`) on one thread, and none of that bookkeeping is written to be
thread-safe.

## Goals / Non-Goals

**Goals:**

- Use more than one core for the per-chunk grid pass.
- Produce a world state that does not depend on thread scheduling, so the parity
  requirement is met by construction rather than by testing alone.
- Keep the blast radius to as few overridden classes as possible, since every
  overridden class must be recompiled from decompiled source and re-verified on
  each game update.

**Non-Goals:**

- Parallelising *within* a chunk. Squares in one chunk overlap each other's
  3×3×3 neighbourhoods almost totally; the locking would cost more than the
  work.
- Making `WorldStreamer`'s queue bookkeeping thread-safe. See Decision 3.
- Touching anything the game already threads, or anything that changes save
  format or network payloads.

## Decisions

### Decision 1: Ship as loose `.class` files, not a patched jar or a Java agent

`ProjectZomboid64.json` declares `"classpath": [".", "projectzomboid.jar"]`.
Because `.` is searched first, a class file under the install directory shadows
the jar's copy with no launcher change at all.

*Alternatives considered.* A patched jar breaks Steam's file verification and
gets re-downloaded. A `-javaagent` that rewrites bytecode at load time is more
robust across game updates, because it can match on patterns rather than on a
whole-class copy — but it requires editing `vmArgs` (which a game update can
revert), and debugging generated bytecode is far slower than debugging Java. The
agent stays the fallback if whole-class shadowing proves unworkable.

*Consequence, and the main schedule risk.* Shadowing means recompiling the
entire class from decompiled source, so cfr's output for `IsoChunk` and
`WorldStreamer` has to recompile and behave identically. cfr emits constructs
that do not always round-trip. This is proven first, before any optimisation
work, because if it fails the whole delivery mechanism changes.

### Decision 2: Parallelise at chunk granularity

One chunk is one task. Chunks that do not touch are independent; squares within
a chunk are not.

### Decision 3: Keep `WorldStreamer` single-threaded and hand only the recalc pass to a pool

Rather than widening `WorldStreamer` to N threads, its one thread keeps owning
the queue and the disk read, and submits only the grid pass to a worker pool,
joining before the chunk is published.

*Why.* `WorldStreamer`'s request lists are plain `ArrayList`s mutated from its
own thread. Widening the thread itself means auditing and locking all of that
bookkeeping — a large, high-risk change to code that is not the bottleneck. The
grid pass is the CPU-bound part; the queue is not.

*Alternative considered.* A full multi-threaded `WorldStreamer`. Rejected for
this change; it can follow later if measurement shows the queue is the limit.

### Decision 4: No adjacency scheduling; publication in submission order

Superseded during implementation. The original decision assumed the streamer
pass writes one tile into neighbouring chunks. It does not: the pass resolves
every neighbour through `IsoChunk.ChunkGetter`, which returns null for any
coordinate outside its own chunk (`IsoChunk.java`, `ChunkGetter.getGridSquare`),
and every lookup in `RecalcAllWithNeighbours(boolean, GetSquare)` — the 3×3×3
loop, `ReCalculateAll`, `doGridNav`, the diagonal fix-ups — goes through that
getter. Cross-chunk boundary recalculation happens later on the game thread in
`doLoadGridsquare()`. Two concurrent passes therefore cannot observe each
other, and the output of a pass is a function of its chunk's data on disk:
parity is by construction, and adjacency ordering would only serialise the
bursts (a burst is one row of mutually adjacent chunks).

What the pool does preserve is the order in which chunks reach the game thread:
a chunk is added to `IsoChunk.loadGridSquare` only after every chunk submitted
before it, so the game-thread fix-ups see the stock sequence.

*Alternatives considered.* Keeping the adjacency rule anyway as belt and
braces — rejected because it removes most of the parallelism the change exists
for, for a hazard the code cannot have.

### Decision 5: Pass the getter per task; loop 1 stays on the streamer thread

Allocate one `ChunkGetter` per chunk task and pass it to
`RecalcAllWithNeighbours(boolean, GetSquare)`; the static stays for any caller
still on the single-threaded path.

Only loops 2–4 of `loadInWorldStreamerThread()` (the roof/rain column pass,
`RecalcAllWithNeighbours` for every square, the `propertiesDirty` pass) run on
the pool. Loop 1 — `RecalcProperties` for every square, with `ensureNotNull3x3`
creating squares — stays on the streamer thread, because it is what creates
squares (`getNew`, `++idMax`) and what first computes polyline-zone outlines on
`IsoMetaGrid`'s shared clipper scratch. After loop 1 those are warmed, and the
`RecalcProperties` re-runs inside loop 3 only read them. This makes a
per-worker `getNew` deque unnecessary: workers never construct squares.

*Alternative considered.* `ThreadLocal` for both. It works and needs no
signature changes, but it keeps the state global and makes it easy to reach the
wrong instance from a nested call. Explicit parameters make the ownership
visible, and the overloads already exist.

### Decision 6: Pathfinding registration stays on the game thread

The stock code already gates `PolygonalMap2` / `PathfindNative`
`addChunkToWorld` behind `Thread.currentThread() == GameWindow.gameThread ||
Thread.currentThread() == GameServer.mainThread`. The pool worker therefore
never satisfies that gate, and the hand-off keeps happening where it does today.
A development-build assertion on entry makes an accidental call from a worker
fail loudly rather than silently skip registration.

### Decision 8: Wake the streamer on enqueue

`threadLoop()` sleeps 140 ms when `jobList` is empty and then falls through to a
second 140 ms sleep at the end of the loop, and takes that end-of-loop sleep
after the last chunk of a burst too. Replace the two fixed sleeps with a
bounded wait on the job queue (a `LockSupport.park` with the same 140 ms bound,
unparked by `addJob`), so the loop keeps its stock behaviour when nothing
arrives and reacts immediately when something does. `addJob` is called from the
game thread; unparking is cheap and never blocks it.

*Why this belongs in this change.* It is the same overridden class, it is what
the measurement identified as ~90 % of chunk latency, and without it the pool's
effect is invisible behind the sleep. Modelled on the recorded baseline: wake
alone takes median chunk latency from 164 ms to 18 ms; wake plus a 4-wide pool
to 6 ms.

*Alternative considered.* Shortening the sleeps — simpler, but trades latency
for wasted wake-ups and still leaves a floor. Switchable separately from the
pool (`wake=false`) so the two effects can be measured apart.

### Decision 7: A runtime kill switch

Parallelism is switchable at runtime and the pool width is configurable, with
width 1 reproducing stock behaviour. This is what makes A/B measurement possible
on one install, and gives a player hitting a problem something to try before
uninstalling.

## Risks / Trade-offs

- **cfr output may not recompile** → Proven in the first task, before any
  optimisation work. If `IsoChunk` or `WorldStreamer` will not round-trip,
  switch to the `-javaagent` approach from Decision 1.
- **An unaudited static on the recalc path corrupts the world** → The four
  `ReCalculate*` routines are already shown clean. `RecalcProperties`,
  `doGridNav` and everything they call still need the same treatment, as does
  `IsoGridSquare.getNew`. The audit is an explicit task and gates the pool being
  widened past 1.
- **Corruption that only appears under load, far from where it was caused** →
  Parity testing runs on a fixed save and a fixed route, and compares full world
  state, not sampled squares. Parity is a precondition for accepting the change.
- **Chunk loading may be I/O-bound, not CPU-bound, for some players** → The
  benchmark reports the before/after honestly, including when it shows no win.
  Keeping `WorldStreamer`'s read on its own thread means the I/O and the compute
  are separately visible.
- **Game updates break the overrides** → A build check refuses to load overrides
  compiled against a different revision, so a stale override fails closed
  instead of running against changed code.
- **More cores on the grid pass may starve the render thread** → Pool width caps
  below the processor count, and worst-percentile frame time is a reported
  metric, so a regression there is visible rather than hidden by a better mean.

## Migration Plan

Install and rollback are file operations: the installer records what it wrote,
uninstall removes exactly that, and the jar is never touched. The kill switch
means a player can fall back to stock behaviour without uninstalling, and a
version mismatch disables the overrides on its own after a game update.
